## 二、相对 V7.2.0 的真实改动（实测对比 `parsed_434.json`）

V7.2.1 不是推倒重来，而是在 V7.2.0 内测基础上**把最后一块拼图（取件地址）补完**，让 6 套正则可定稿。共 3 类改动：

### ① 取件地址：两套公式合并为单条优化公式（核心改动）

| 版本 | 取件地址正则 |
|------|-------------|
| V7.2.0 | 两套：`取件地址1`(`到达(?:「)?`) 与 `取件地址2`(`到达?(?:「)?`) 分别匹配、逐级命中即止 |
| V7.2.1 | **单条** `取件地址`：`(?<=暂存)\S+\s?\d+?(?=，暂存码)\|他人签收\|(?<=至\|前往\|由\|已?放?在\|已?暂存在?\|暂存到\|到达「\|到「\|到达\|到(?!达))\s*([^\s到「，凭在码]+?(?:站点)?)\s*(?=\s*(?:代签\|滞留\|请凭\|免费\|领?取件?\|暂存码\|取件码\|取货码\|码\|[，,]))` |

**改动点（v3 语义化重构）**：
- `到达` → `到(?!达)`：用定长负向先行强制完整消耗「到达」，根因是「最左匹配」会把「达」残留在提取值开头。
- 主体排除集加 `码` + 结尾哨兵显式列出 `暂存码\|取件码\|取货码\|码`：修复真实短信「院子馨月湖南门店**码110226**」越界（原 `暂?存` 分支误吞「门店码」裸码）。同时覆盖 `暂存码：` / `暂存码"` / `暂存码 222111` / `暂存码"1111122"` 等变体。
- 新增 `已?暂存在?` / `暂存到` 分支：统一「暂存在 XX」「暂存到 XX」「暂存XX地方」三种语义。
- **动作数 −8**：合并掉一套「地址2」的 Text Match + If + 变量链。

### ② 自动化开关默认 `True`

V7.2.0 内测时 `自动化` = `False`（不自动建列表）；V7.2.1 改为 `True`，首次运行即自动创建「提醒事项」App 的「待取件📦」列表，零配置开箱即用。

### ③ 版本号 `7.2.0` → `7.2.1`

字典 `版本号` 键同步更新，供在线更新检查比对。

> 取件码 / 运单号 / 尾号 / 特殊格式取件码 / 关键词 **5 套正则与 V7.2.0 逐字相同，无提取能力变化**（V7.2.0 阶段这 5 套已是最优态，V7.2.1 直接沿用）。6 套正则的优先级链设计完全保留。

## 五、工作流机制分解（128 动作，按真实执行顺序）

| 阶段 | 动作索引 | 机制 | 关键设计 |
|------|---------|------|---------|
| ① 配置+注释 | i1–2 | Comment 载入；Dictionary 载入配置（14 键） | 一次载入，全程引用 |
| ② 输入 | i3–4 | Get Text from Input 取短信 → Set Variable `express_messages` | 输入 = 自动化传入的「输入快捷指令的信息」 |
| ③ 取件码类优先级链 | i5–8, i12 | 5 个 Text Match：取件码→运单号→尾号→特殊格式取件码→**关键词** | 命中即止 |
| ④ 优先级判断 | i9–16 | If 逐级下探，全未命中则 Exit | 保底不误处理 |
| ⑤ 在线更新检查 | i17–23 | Base64 解更新URL → Get Contents of URL 拉 version.json → Detect Dictionary → 取 `最新版本号` | 有新版则 Notification |
| ⑥ 更新提示 | i24–36 | If 有更新 → Alert + Showwebpage（指向更新页）→ Exit | 不影响正常提取路径 |
| ⑦ 开关展开 | i37–42 | If + Set Variable：`pickup_list.name` / `pickup_add.status` / `pickup_show.status` / `auto.status` | 把字典 4 个开关转成变量 |
| ⑧ 列表准备 | i43–55 | Filter / Create「待取件📦」；`auto.status=True` 时自动建列 | 列表不存在则新建 |
| ⑨ 多取件拆分 | i56–58 | Text Split 按分隔符拆多条 → Repeat with Each → `express_sms` | 一条短信多包裹 |
| ⑩ 提取+组装 | i59–106 | Text Match / Replace / Combine → `pickup_codes` / `pickup_name` / `pickup_add` / `pickup_code.txt` | 按「显示格式」拼文案；地址走单条合并公式 |
| ⑪ 去重+写入+通知 | i107–128 | Filter Reminders → Repeat 比对取件码 → 已存在则标记旧完成+通知，全新则 Addnewreminder → Delay | 智能去重，最后 Delay 错开节奏 |

### 三条核心机制
- **机制 A（取件码类优先级链）**：取件码 → 运单号 → 尾号 → 特殊格式取件码 → 关键词，**必须逐级、命中即止**。
- **机制 B（取件地址类优先级链）**：V7.2.1 为**单条合并公式**一次性匹配（已内建 `到(?!达)` + `码` 防御，覆盖原地址1/地址2 全部场景），不再分两套。
- **机制 C（去重写入）**：写入前先 Filter Reminders 拉「待取件📦」全部项 → 遍历比对取件码：已存在则标记旧提醒完成+通知，全新则新增；最后 Delay 错开节奏。

## 六、iOS 兼容性（实测结论）

- **兼容 iOS 26 系统**；**兼容 iOS 18 部分版本**（需 iOS 18.x 较新小版本）。
- 依据：6 套正则含 `(?<=…)` 定长/变长 lookbehind 与 `(?!…)` / `(?=…)` lookahead。iOS 16.4+ 的 JS 引擎才支持 lookbehind；**变长 lookbehind 依赖更新版 ICU，iOS 18 早期小版本可能不支持**，故标注「iOS 18 部分版本」。
- 验证方式：用 Node V8 引擎（与 iOS 同内核）对 6 套公式逐条 `new RegExp()` 编译 + 样例命中，6/6 全部通过，无「invalid lookbehind」类错误。
- 特殊格式取件码的正则**未改**，保持原样（仅 1 个样本，按约定不冒险）。

## 七、iOS 自动化触发配置（硬约束）

- **触发条件**：`信息 包含 【`（左方括号 【，U+3010，**不是右方括号 】**）
- **执行动作**：`运行 快递取件码 V7.2.1` + 输入选 `输入快捷指令的信息`
- ⚠️ **运行前确认必须关闭**：若开启，每条短信需手动点确认才能运行，自动化失去意义。自动化开关 ✅ 开启 + 运行前确认留空不勾 = 真正全自动。
- 「从 无处 接收…」是选了输入变量后系统自动生成的副产物，非独立配置项、部分版本不显示，文档化忽略不计。

## 八、小白用户使用约定

- **不建议修改快捷指令本身**：6 套正则 + 优先级链是精密结构，乱改动作/字典易致提取失效。
- **首次使用三步必做**：① 建「信息 包含 【」短信触发自动化（运行前确认关）；② **手动跑一遍快捷指令** + **手动触发一遍自动化**；③ 弹出任何权限（提醒事项/通知/网络等）**一律授权**，否则核心功能不可用。
- 权限弹窗仅首现一次，漏授权会"装了没反应"，教程须主动提示用户授权。

## 九、遗留小问题（非 V7.2.1 回归，继承自 V7.2.0）

- `关键词` 正则里 `兔喜生活| 近邻宝` 的 `近邻宝` 前带一个**前导空格**（`| 近邻宝`），实际只会匹配「 近邻宝」（带空格），正常短信中几乎不会出现，等于该关键词失效。属预存瑕疵，不影响主流程（取件码/运单号提取不依赖它），可在后续版本清理。
